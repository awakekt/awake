    Launch parameters and host actions

    Read what a game was launched with, such as a server name or a debug flag, the same way on every platform, learn where the page was served from and whether the device is touch-first, and ask the host to open a link or reload the page.

    module: com.awakekt.awake.engine:window Desktop · Android · iOS · Web

    A launch parameter is read from a different place on each platform: the page URL in a browser, the command line on desktop, the launch Intent on Android, the launch URL on iOS. LaunchParameters puts them in one shape, so game code reads a parameter once and each platform's entry point decides where it comes from. HostActions is a separate service for the things a game asks of its host: openUrl everywhere, and pageReload on the web only. LaunchEnvironment reports what the host knows about itself: the page's origin on the web, and whether the device is touch-first or pointer-first.

    Launch parameters are untrusted input

    A link, a shortcut or a command line that anyone can share controls them. A page opened as https://game.example/?server=evil.example names whatever server its author likes, and an Android app can be launched with extras by any other app. Validate every value before using it: check a server against an allow-list, a number against its range, a mode against the modes you have. Never pass one unchecked to a file path, a network address, a shell or openUrl. A key can also repeat any number of times, so bound how many values you read.

    Read the parameters

    Build the parameters in the platform entry point and register them as a service. Game code in commonMain then looks them up without knowing where they came from.

    wasmJsMain
    val app = app {
    service(LaunchParameters::class, browserLaunchParameters())
    service(HostActions::class, browserHostActions())
    service(LaunchEnvironment::class, browserLaunchEnvironment())
}
    desktopMain
    fun main(args: Array<String>) {
    val app = app {
        service(LaunchParameters::class, desktopLaunchParameters(args))
        service(HostActions::class, desktopHostActions())
        service(LaunchEnvironment::class, desktopLaunchEnvironment())
    }
}
    androidMain
    class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        val app = app {
            service(LaunchParameters::class, intent.launchParameters())
            service(HostActions::class, androidHostActions(this@MainActivity))
            service(LaunchEnvironment::class, androidLaunchEnvironment(this@MainActivity))
        }
    }
}
    iosMain
    // launchUrl is the URL the host app received in application(_:open:options:), or null.
fun makeViewController(launchUrl: String?): UIViewController {
    val app = app {
        service(LaunchParameters::class, iosLaunchParameters(launchUrl))
        service(HostActions::class, iosHostActions())
        service(LaunchEnvironment::class, iosLaunchEnvironment())
    }
    // ...
}

    Then read them anywhere:

    commonMain
    val parameters = lifecycle.requireService<LaunchParameters>()

val server = parameters.first("server")?.takeIf { it in allowedServers } ?: defaultServer
val tags = parameters.values("tag").take(8)
val debug = parameters.has("debug")
    Member Returns
    has(key) True when the key was passed, with a value or as a bare flag.
    first(key) The first value, or null when the key is absent. "" for a bare flag.
    values(key) Every value in order, or an empty list. A repeated key keeps all of them.
    keys The keys in the order they first appeared.
    toMap() A copy: each key with its list of values.

    A bare flag and an empty value are the same: ?debug and ?debug= both give "". A browser cannot tell them apart, so no platform does. toString() lists the keys and never the values, so a token in a link does not reach a log.

    Parsing rules

    The rules live in common code, in LaunchParameters, and each platform reads its source through one of them. The same parameters give the same result everywhere; the tests state one set of parameters in each encoding and compare.

    Source Rule
    Web: page URL query
    fromQuery    		 Like URLSearchParams. One leading ? is dropped, & separates, an empty part is skipped. A part splits at its first =, so token=a=b is a=b; no = is a bare flag. + is a space and %XX a UTF-8 byte, in keys and values; a malformed % stays as written and invalid UTF-8 becomes U+FFFD. The #fragment is never read.
    Desktop: main arguments
    fromArguments    		 --key=value splits at the first =; --flag is a bare flag. Values are taken as given, with no percent-decoding. --key value is not a pair: --key is a flag and value is a stray argument, because a flag followed by a positional argument would otherwise swallow it. Anything not starting with -- is ignored, and a bare -- ends the options.
    Android: launch Intent
    Intent.launchParameters()    		 First the data URI's query, read as the web rule, then the extras. A String or other CharSequence extra is one value. A boolean, number or Char extra is its toString(). A String[] or list of text is one value per element, so a repeated key survives. A null extra is a bare flag. A Bundle, a Parcelable, a primitive array or an extra the system cannot unparcel is skipped.
    iOS: launch URL
    fromUrl    		 The query of the URL, read as the web rule. The part before ? and the #fragment are ignored.

    For every source: a repeated key keeps all its values in order, an empty key is dropped, keys are case-sensitive, and nothing is trimmed or validated.

    iOS

    iOS hands the launch URL only to the app delegate (application(_:open:options:), or onOpenURL in SwiftUI). That is host app code, not part of this library, so the library cannot read it. The host app passes the URL string in: iosLaunchParameters(url.absoluteString). A launch from the home screen has no URL, and iosLaunchParameters() returns empty parameters.

    Launch environment

    LaunchEnvironment holds two values the host reports about itself, read once when the factory is called. It is a sibling of LaunchParameters, not part of it: the parameters are what the launcher was given, and the environment is what the host is.

    commonMain
    val environment = lifecycle.requireService<LaunchEnvironment>()

// A default server next to the page, or the configured one off the web.
val server = environment.origin
    ?.let { origin -> "${if (origin.isSecure) "wss" else "ws"}://${origin.host}:${origin.effectivePort}/play" }
    ?: configuredServer

val hud = when (environment.primaryInput) {
    PrimaryInput.Touch -> TouchHud
    PrimaryInput.Pointer -> PointerHud
}
    Platform origin primaryInput
    Web The page's scheme, host and port, from location.href. null for a file: page and other opaque origins. Touch when matchMedia('(pointer: coarse)') matches, Pointer otherwise.
    Desktop null: a desktop app is not served from a page. Pointer, touchscreen laptops included.
    Android null: a link that opened the app is a launch parameter. Touch when the device has the android.hardware.touchscreen feature, Pointer otherwise (a TV, a desktop-mode device).
    iOS null: a universal link's host is a launch parameter. Touch, an iPad with a trackpad and the app on a Mac included.

    LaunchOrigin.fromUrl reads the origin the way a browser's location does: only http and https have one; scheme and host are lower-cased; user info is dropped; an IPv6 host keeps its brackets; and port is null when the URL names none or names the scheme's default, as location.port does. effectivePort fills the default in (443 or 80), and toString() writes the origin as location.origin does. A port that isn't a decimal number from 0 to 65535 means there is no origin.

    The primary input can change while the game runs: a tablet gains a mouse, a laptop folds into a tablet, a browser's device emulation is switched on. LaunchEnvironment does not follow it, so the value stays what it was at launch. Use it to pick the first HUD, then switch on the input the game actually receives.

    Hints, not security boundaries

    The origin is whoever serves this copy of the page: a mirror, a proxy or a local copy can serve the same game from any host. The primary input is the platform's guess about the device. Use both to choose defaults, such as a server address or a HUD layout. Never use them to decide what a player may do, and validate an address built from the origin as you would any other input.

    Host actions

    HostActions is separate from LaunchParameters because it is a different capability: it does something, rather than report something.

    commonMain
    val actions = lifecycle.requireService<HostActions>()

if (!actions.openUrl("https://example.com/help")) showLink("https://example.com/help")

// Reload exists only where it has a meaning. Ask first.
actions.pageReload?.let { reload -> button("Reload") { reload.reload() } }
    Platform openUrl pageReload
    Web window.open in a new tab with noopener,noreferrer. Returns true once called; a popup blocker may still refuse a tab opened outside a user gesture, so call it from an input handler. Present: reloads the page.
    Desktop AWT Desktop.browse. Returns false, never throws, with no display (headless, CI), no browse support, or on failure. null
    Android Intent.ACTION_VIEW with the browsable category. Returns false when no app handles it. null
    iOS UIApplication.open on the main queue. Returns true once requested; iOS reports the result later. null

    pageReload is a capability check, not a method that does nothing elsewhere: it is null off the web. What reload would mean on desktop or mobile (restart the process, re-run bootstrap) is not decided, so it is not offered there.

    openUrl only opens absolute http, https and mailto URLs. file:, javascript:, intent:, custom app schemes and anything with whitespace or control characters are refused with false, so a URL built from a launch parameter or a network message cannot reach another app's handler or the local disk. That does not make a link from a launch parameter safe to follow: it can still send the player to a site its author chose. Show where it leads, or check the host against a list.

    macOS

    On macOS, GLFW needs the JVM's first thread (-XstartOnFirstThread) and AWT wants it too. Test openUrl in your macOS build before relying on it.
