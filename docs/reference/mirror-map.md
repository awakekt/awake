# Mirror Map: Awake UI DSL vs. Jetpack Compose

Awake's retained Compose-shaped UI API (`Modifier`, `Row`/`Column`/`Box`, state hooks,
`animateFloat*`, `graphicsLayer`) is deliberately shaped to *feel* like Jetpack Compose --
chainable modifiers, slot-lambda scopes, `weight()`, `remember`-style state,
`animateFloatAsState`-style helpers -- so that
a Compose developer's muscle memory transfers. It is not a Compose-compiler-plugin
runtime: there is no recomposition, no snapshot state, no constraint negotiation.
Following `kotlin-multiplatform-api-mimicry`'s method, this doc catalogs each mimicked
primitive against Compose's real current public shape and calls out three states:
**Faithful** (same ergonomics, same behavior a Compose developer would expect),
**Diverges** (looks Compose-shaped but behaves differently -- the dangerous category,
since it passes a glance-review and then causes a layout/render bug later), and
**Not implemented** (a real gap, not necessarily a deviation). Every row below is backed
by a direct read of the current source under
`awake/compose/ui/src/commonMain/kotlin/io/github/awakelab/awake/compose/ui/` (runtime and state hooks)
and `awake/ui/animation/src/commonMain/kotlin/io/github/awakelab/awake/ui/`
(animation primitives) -- corrected 2026-08-21, the previous `awake/engine/ui/ui-core/...`
path does not exist in this repo (verified: `awake/engine/ui/` contains only an empty
`ui-shadcn/` leftover) -- not
memory of Compose or of this codebase from an earlier session.

Use this doc before reaching for a Compose idiom in Awake code: check whether the row
below says "Faithful" (safe to assume Compose semantics) or "Diverges" (read the
deviation detail first).

> **Companion doc**: [`compose-modifier-layout-guidance.md`](compose-modifier-layout-guidance.md)
> covers *how* to use every `UiModifier` correctly with code examples, safe patterns, and
> what is not yet implemented. This `MIRROR_MAP` is the status table; that doc is the how-to guide.

## Which upstream a given API mirrors (read this before checking anything against Compose)

Everything below this section maps *infrastructure* — modifiers, the layout DSL, state hooks,
animation, `graphicsLayer` — and for those, Compose is the right thing to check against.
Components are a different question, and the answer is not Compose Foundation.

Classifying the retained Compose Foundation and Design System public functions (audited 2026-08-28):

| Bucket | Count | Upstream to check against |
|---|---|---|
| Layout/text/draw primitives — `box`/`row`/`column`/`spacer`, `text`→`BasicText`, `textField`/`textarea`→`BasicTextField`, `canvas`→`Canvas`, `icon`/`textureQuad`→`Image`, `surface`≈`Box`+`background`/`border`/`clip`, `interactiveSurface`≈`Box`+`clickable` | 12 | **`compose-foundation`** |
| Overlay hosts — `popup`, `dialog` | 2 | **`compose-ui`** (`androidx.compose.ui.window`) |
| Controls — `button`, `checkbox`, `radio`, `switch`, `slider`, `rangeSlider`, `progress`, `separator`, `select`, `combobox`, `menuItem`, `contextMenuTrigger`, `toggle`, `toggleGroup`, `toast`, `spinner`, `skeleton`, `avatar`, `collapsible`, `otpInput`, `resizablePanelGroup` | 21 | **Radix / Base UI anatomy** |
| Infrastructure — `uiScope`, `frameBounds`, `remember*`, `provideTextStyle`, `animateFloatTween`, `resolveGlyphPx`, `withIntrinsicLabelSize`, … | 12 | **`compose-runtime`/`compose-ui`**, per the tables below |

**Foundation contains no controls.** No `Button`, no `Checkbox`, no `Switch`, no `Slider` —
Compose ships every one in Material. So "does real Compose have this?" is unanswerable when
aimed at a control, and Material's own signatures (`Button(onClick, colors, elevation, …)`)
fuse visual parameters `ui-headless` is forbidden to carry. For those 21, the upstream that
actually matches is Radix, which is what shadcn is built on — recorded in the pinned reference
id itself, `shadcn-6261bd8-new-york-v4-radix-1.4.2`.

Practical consequence: a control whose styling can only be reached through a growing list of
`*Style` parameters is missing a *part*, not a parameter. `combobox` carries five
(`style`/`selectedStyle`/`optionStyle`/`filterStyle`/`surfaceStyle`); in Radix anatomy those
are `Trigger`/`Positioner`/`Popup`/`Item` elements, each styled where it is rendered. Four of
the five defects fixed in `12882c186` were exactly that shape — no panel surface (no `Popup`),
popup width pinned to the trigger (no `Positioner`), selected style replacing rather than
layering (no `Item` state), and rows centred because `menuItem` inherited a `button` default.

## `UiModifier`

Source: `modifier/UiModifier.kt`, `LayoutModifiers.kt`, `StyleModifiers.kt`,
`ScrollModifiers.kt`, `StateModifiers.kt`, `GraphicsLayer.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Modifier` chain (immutable, `then()`-composed) | `UiModifier` data class + extension functions returning `copy(...)` | Faithful | Chaining reads identically (`Modifier.padding(...).width(...)`); internally it's a flat data-class overwrite, not a linked list, but that's an implementation detail invisible at the call site. |
| `Modifier.width`/`.height`/`.size` | `UiModifier.width`/`.height`/`.size` (`LayoutModifiers.kt`) | Faithful | Same fixed-size semantics. |
| `Modifier.fillMaxWidth`/`.fillMaxHeight`/`.fillMaxSize` | Same names (`LayoutModifiers.kt`) | Diverges | Looks identical, but "fill" is resolved per-child against the *parent's configured size*, not against real remaining-constraint math the way Compose's `Constraints` propagation works -- see the `weight()` row below for the concrete failure mode this causes. |
| `Modifier.weight(1f, fill = true)` inside `Row`/`Column` | `UiModifier.weight(weight, fill)` inside `row()`/`column()`, distributed by `resolveWeightedMainAxis()` (`Arrangement.kt`) | Faithful (fixed) | Was a real, already-hit bug class this session (`shadcnField*` controls, checkout-form grid row, `shadcnToggleGroup`) -- `resolveWeightedMainAxis()` used to sum non-weighted siblings' *trial-measured* size into `nonWeightedOccupied`, so a non-weighted `fillMaxWidth()` sibling's trial claim (an artifact of cursor position, not a real reservation) could starve weighted siblings to zero depending on measurement order. Fixed in commit `9455bc51`: a new `fillsMainAxis` signal (threaded through `UiMeasuredContent`/`UiContext`/`RowScope`/`ColumnScope`) now lets the resolver give weighted siblings their proportional share *first* (matching Compose's real constraint-propagation order), then hands non-weighted `FillMax` siblings whatever's left -- which is correctly zero when they're genuinely contending for the same axis, not an order-dependent accident. Verified order-independent via tests in both sibling orderings. The 3 existing `weight(1f)` workarounds at the call sites above were left in place (still correct, just no longer the only option) -- reverting them to `fillMaxWidth()` is a safe, optional cleanup, not required. |
| `Modifier.align(Alignment)` inside `Row`/`Column`/`Box` | `UiModifier.align(UiAlignment)` | Faithful | Per-child cross-axis override, same as Compose's `RowScope.align`/`ColumnScope.align`/`BoxScope.align`. |
| `Modifier.offset(x, y)` | `UiModifier.offset(x, y)` | Faithful | Same additive-post-layout-offset shape. |
| `Modifier.padding(...)` (all four overload shapes) | `UiModifier.padding(...)` (`LayoutModifiers.kt`) | Faithful | Same all/horizontal-vertical/per-edge overload set. |
| `Modifier.background(Color)` / `.border(width, color)` / `.clip(shape)` | `UiModifier.background(Color)` / `.border(width, color)` / `.shape(radius)` (`StyleModifiers.kt`) | Faithful (ergonomics) | Call-site shape matches; internally these route through a separate `Style` object (`styleable()`) rather than being pure per-widget modifier fields -- documented deliberately in `UiModifier.kt`'s own class doc as "modifier is structure/behavior, style is visuals," a split real Compose doesn't make this explicitly. Doesn't change caller-observable behavior. |
| `Modifier.verticalScroll(state)` / `.horizontalScroll(state)` | Same names (`ScrollModifiers.kt`) | Diverges (corrected 2026-08-21 -- this row previously read "Faithful (ergonomics)", which contradicted both its own deviation detail below and this table's own Tally section, which already counted "scroll-modifier overwrite" as one of the 4 Diverges items; the sibling `compose-modifier-layout-guidance.md` doc's Scroll section already had this right) | Same call shape; both calls just set the same `scrollState`/`scrollConfig` fields, so a modifier chain with both `.verticalScroll(...)` and `.horizontalScroll(...)` silently has the second call overwrite the first (no bidirectional scroll) -- Compose's two functions are independently composable via nested containers, this pair is not. Minor, but a chain like Compose code would naturally write (`.verticalScroll(v).horizontalScroll(h)`) does not do what it looks like. **Real default-styling bug found and fixed (this session, `ScrollContainers.kt`'s `scrollPanel()`)**: `column(id, modifier = Modifier.verticalScroll(state))` with no `style` at all silently rendered as a themed card -- border + `card` background -- because `scrollPanel()` unconditionally passed `defaults = currentTheme.components.surface` into `resolveStyle`, regardless of whether the caller's own style resolved any visuals. The non-scroll column path (`resolveMeasuredColumn`, gated by `smartColumn`'s `hasResolvedVisuals` check) never had this problem -- a bare non-scroll `column()` stays invisible unless its own `style` asks for a background/border. In Compose, `Modifier.verticalScroll()` never paints anything by itself; this divergence had no Compose analog and no signature-diff-based audit pass could have caught it, since the API *shape* (`verticalScroll(state)`, same name, same param) was already faithful -- the bug was purely in *default runtime behavior* baked into an internal `defaults =` argument, invisible to a pure API-surface comparison. Fixed by changing `scrollPanel()`'s `defaults` to the same neutral `Style { shape(UiShape.md); borderWidth(UiShape.none) }` base `surface()` (`layouts/Surface.kt`) already uses -- a bare scroll column now stays invisible by default like its non-scroll counterpart, and only paints when the caller's own `style` sets a background/border. |
| `Modifier.clickable(enabled, onClick)` | `UiModifier.clickable(enabled, onClick)` (`ClickableModifiers.kt`), resolved via `UiScope.resolveClickable(id, slot, modifier)` | Diverges | Call shape (`Modifier.clickable(enabled = ..., onClick = { ... })`) and click semantics (must press *and* release inside the same bounds, matching `button`/`checkbox`'s existing `interact()` press-release-inside behavior in `ui-headless`) are faithful. What diverges: Compose's `Modifier.clickable` works on *any* composable automatically, because Compose's pointer-input pipeline is wired to every layout node by the framework. Awake's version does not -- it's an opt-in field (`UiModifier.clickAction`) that a widget's own implementation must explicitly resolve by calling `resolveClickable(id, slot, modifier)` at the same point it already resolves `forceHover`/`forceActive`/`forceFocus`, using that widget's own stable `id` as the active-state key (Awake's click detection is id-based via `tryClaimActive`/`isActive`, not automatic per-composable identity the way Compose's is). Piloted on `surface()` (`ui-core/layouts/Surface.kt`) -- chosen because `surface()` had *zero* built-in click semantics before this (unlike `button`/`checkbox`, which already hand-roll their own `interact()` call and were deliberately left unmigrated, out of scope for this pass), so it's the clearest proof the mechanism works standalone via the modifier alone. Built entirely on top of the pre-existing `hitTest()`/`tryClaimActive()`/`isActive()`/`releaseActiveIfMatches()` primitives -- not a parallel input pipeline. No `Modifier.pointerInput { }` escape hatch was added (YAGNI -- no real call site needed raw press/drag/move tracking yet; add one if/when a consumer needs lower-level gesture data than `clickable` exposes). |
| `Modifier.graphicsLayer { rotationZ = ...; scaleX = ...; alpha = ... }` | `UiModifier.graphicsLayer(effect: UiGraphicsEffect)` (`GraphicsLayer.kt`) | Diverges (partially, alpha and scale are real) | See the dedicated GraphicsLayer section below -- `UiAlphaEffect` and `UiScaleEffect` now carry real values applied at `UiContext`'s emission choke point (alpha CPU-side, scale GPU-side), but rotation/shadowElevation/clip-transform are still not implemented and the call shape is still `graphicsLayer(SomeEffect)`, not a configuration lambda. |
| `Modifier.testTag(tag)` | `UiModifier.testTag(tag)` (`StateModifiers.kt`) | Faithful | Same purpose (test-hook id), same shape. |
| `Modifier.zIndex(...)`, `Modifier.rotate/scale/alpha` as top-level modifiers (Compose has both a top-level shorthand and the `graphicsLayer{}` block form) | `UiModifier.alpha(value)` / `UiModifier.scale(scaleX, scaleY, pivotX, pivotY)` (`GraphicsLayer.kt`) exist as standalone shorthands; rotate/zIndex do not | Diverges (alpha, scale), Not implemented (rotate/zIndex) | `alpha(value)` and `scale(...)` are real (build a `UiAlphaEffect`/`UiScaleEffect`), matching Compose's top-level-shorthand ergonomics. No standalone rotate/zIndex modifier functions exist. |

## `UiScope`/`row()`/`column()`/`box()` DSL

Source: `layouts/Row.kt`, `Column.kt`, `Box.kt`, `RowScope.kt`, `ColumnScope.kt`,
`BoxScope.kt`, `AbsoluteScope.kt`, `Arrangement.kt`, `Layout.kt`, `RootLayouts.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Row(horizontalArrangement, verticalAlignment) { }` | `row(horizontalArrangement, verticalAlignment, modifier, id, cacheKey) { }` (`Row.kt`) | Diverges (default arrangement value, corrected 2026-08-21) | Named-parameter shape and `verticalAlignment` default (`UiAlignment.Vertical.Top`, matching Compose's real `Row` default) are faithful, but the previous row text's claim that `defaultArrangement()` is "`Arrangement.Start`-equivalent" is factually wrong -- verified against `defaultArrangement()`'s real body (`layouts/Arrangement.kt:130`): `fun defaultArrangement(): Arrangement = Arrangement.spacedBy(8f.dp)`. Compose's real `Row` defaults `horizontalArrangement` to `Arrangement.Start` (children packed together, zero gap); Awake's every `row()` overload (`ColumnScope.row`/`RowScope.row`/`AbsoluteScope.row`/`BoxScope.row`/`UiPrimitiveScope.row`, all in `Row.kt`) defaults to an **8dp gap between every child** instead. A caller who omits `horizontalArrangement` expecting Compose's packed-together default gets unrequested spacing with no compile-time signal -- pass `horizontalArrangement = Arrangement.Start` explicitly to get Compose's actual default behavior. See the new "Layout DSL" section of `compose-modifier-layout-guidance.md` for the how-to. |
| `FlowRow` / `FlowColumn` | `FlowRow` / `FlowColumn` (`Flow.kt`) | Faithful subset | Foundation flow layouts wrap children into new rows or columns only on a bounded main axis, preserving one line when unbounded unless an explicit item cap applies. Both axis arrangements distribute the items within each line/column and the lines/columns within the container; scoped/default cross-axis and alignment-line placement plus per-line weights are supported. `maxLines` collapses later children. AndroidX's dynamically composed overflow-indicator API is deprecated upstream and requires multi-content subcomposition, deliberately absent from Awake. |
| `Column(verticalArrangement, horizontalAlignment) { }` | `column(id, verticalArrangement, horizontalAlignment, modifier, style, cacheKey) { }` (`Column.kt`) | Diverges (default arrangement value, corrected 2026-08-21) | Same divergence as the `Row` row directly above -- `column()`'s `verticalArrangement` also defaults to `defaultArrangement()` = `Arrangement.spacedBy(8f.dp)`, not Compose's real zero-gap `Arrangement.Top` default, while `horizontalAlignment`'s default (`UiAlignment.Horizontal.Start`) does match Compose's real `Column` default. The previous row text ("Same shape.") didn't make an explicit claim about the default and so wasn't wrong, but was silent about this real, load-bearing gap. |
| `Box(contentAlignment) { }` | `box(modifier, contentAlignment) { }` (`Box.kt`) | Diverges (default size, corrected 2026-08-21) | `contentAlignment` as a named param (not a modifier) is faithful. Not faithful: Compose's `Box` with no size modifier shrink-wraps to its children's measured size (like Awake's own `WrapContent`); Awake's `box()` primitive (`UiPrimitiveScope.box`, `Box.kt`) claims its slot via `modifier.withSizeFallback(Dimension.FillMax, Dimension.FillMax)` -- a bare `box { }` with no explicit `.width()`/`.height()` fills its parent's configured axis on both dimensions instead of hugging its content. The previous row text made no claim about default sizing and was silent about this. See `compose-modifier-layout-guidance.md`'s new "Layout DSL" section. |
| `Arrangement.Start/Center/End/SpaceBetween/SpaceEvenly/SpaceAround/spacedBy(dp)` | Same set, `Arrangement` sealed interface (`Arrangement.kt`) | Faithful | Free-space math for `Center`/`End`/`SpaceBetween`/`SpaceEvenly`/`SpaceAround` in `Arrangement.plan()` matches Compose's own formulas (leading/between space split). |
| Compose's `Constraints`-based measure/layout pass (single measure pass per composition, min/max bounds propagated top-down, `Layout`/`MeasurePolicy`) | A **trial-measure-then-real-measure** two-pass model added for `weight()` support (commit `8f421138`), later fixed for redundant-recursion perf (commit `3f86853e`), partially optimized again in commit `55dd0681`, and given a reusable-trial-context perf fix in a follow-up commit this session | Diverges | Every `row()`/`column()` call with a `WrapContent` axis or any weighted/measured-distribution arrangement pays a throwaway "trial" measurement of its own `content` lambda (`context.measureRowContent`/`measureColumnContent`) purely to learn sizes/weights, then measures again for real placement -- unlike Compose, which measures each child exactly once per composition via `Constraints` negotiation. This is a real perf/behavior difference (side-effecting code inside a `row {}`/`column {}` body, e.g. `animateFloat`, must special-case `isMeasuringInternal()` to avoid double-stepping during the trial pass -- see `UiAnimation.kt`'s explicit guards) that has no Compose analog: a Compose composable body never re-executes to "trial measure" itself this way. **Partial optimization, not a fix of the underlying model** (commit `55dd0681`, see `docs/tasks/archive/2026-08-02-trial-measure-double-execution.md`): real profiling found `UiScope.row()`/`column()` additionally ran its own `hasWeightedChild`-detection trial *unconditionally*, even for `Center`/`End`/`SpaceBetween`/`SpaceEvenly`/`SpaceAround` arrangements (`Arrangement.requiresMeasuredDistribution()`) where that trial's result is provably irrelevant -- those arrangements always take the `plannedSlots` branch regardless of `hasWeightedChild`. Reordering the check to short-circuit the trial in that case cuts per-level content-lambda executions from 3 to 2 for nodes using those five arrangements specifically (a synthetic ui-core benchmark, `TrialMeasureScalingTest`, measured this as a 3^depth -> 2^depth reduction: depth-8 trial count dropped from 86,093,441 to 131,071 in a worst-case nested chain). This does **not** touch the common case -- a plain `Arrangement.Start`/`spacedBy` row or column with a weighted child still pays its own unconditional detection trial, since there's no way to answer "does this content have a weighted child" without executing it once first, and eliminating that requires either a lazy children-gathering phase or per-call-site-id caching, both explicitly scoped out as future, dedicated design work (not attempted here). Real-world impact is arrangement-usage-dependent: ui-showcase's Checkout Form page (the profiling target) uses only `spacedBy`, so its trial count is measurably unchanged by this fix (still 7,696 passes) -- the win is real but currently only reaches pages/components that use the five affected arrangements. **Second, separate fix (this session, per `docs/tasks/archive/2026-08-02-trial-measure-double-execution.md`'s "approach B")**: `UiContextMeasureState.createMeasureContext()` used to allocate a brand-new `UiContext` object graph (plus its `beginFrame`/`pushTextStyle`/`pushFont`/`pushTheme` calls) on *every* trial pass; it now caches and reuses one trial `UiContext` per owning `UiContextMeasureState` instance (scoped 1:1 to whichever real or trial context owns it, never shared across owners, never reentered), resetting its theme/font/textStyle stacks in place instead of pushing onto a fresh stack each time (`UiContextStacks.resetForTrial`). Real measured numbers (new `UiMeasureTrialStats.contextCtorNanos` counter, Checkout Form page, 7,696 passes/frame): construction/`beginFrame`/push cost dropped from 4.516ms to 1.197ms of the total trial-measure time, but that construction cost was itself only ~9.4% of the 48.064ms trial-measure total pre-fix -- so total trial-measure time dropped only modestly, from ~48.06ms to ~44.4-44.7ms (~7% off trial time, ~1-2ms off total frame time; trial *pass count* is unchanged at 7,696, since this fix targets fixed per-trial cost, not pass count). Confirms the original doc's own honest caveat ("a constant-factor win... 20-40% off trial time, unverified") was optimistic -- object-graph construction was real but a minority of trial cost; the large majority is the trial content lambda's own layout/arrangement/text-measurement work, untouched by this fix. The two-pass trial-measure model itself remains unchanged and still diverges from Compose's single-pass `Constraints` propagation for the general case; eliminating the *pass count* (not just fixed per-pass cost) still requires the lazy-children-gathering or per-call-site-id caching work named above. **Third fix, the per-call-site-id caching work itself (this session, `docs/tasks/archive/2026-08-02-trial-measure-cross-frame-cache.md`)**: `UiScope.row()`/`UiScope.column()` gained opt-in `id`/`cacheKey` parameters (mirroring `animateFloat(id, ...)`'s identity model, `UiAnimation.kt`) that cache *only* the `hasWeightedChild` boolean -- never sizes/positions, to avoid reintroducing the staleness class `WrapContentMeasurementStateTest` guards against -- across frames in the real widget-state store, skipping the detection trial entirely on a cache hit. Both default to `null`; every pre-existing call site is unaffected. A debug/test-only consistency check (`UiWeightCacheConsistencyCheck.enabled`, off by default, same zero-cost-when-disabled contract as `UiMeasureTrialStats.enabled`) re-runs the real trial on every cache hit and throws if it disagrees with the cached answer, catching a caller's stale `cacheKey` loudly in tests instead of shipping wrong layout silently -- verified by `RowColumnWeightCacheTest`'s three cases (cache-hit, cache-invalidation, stale-key-caught-by-consistency-check). Confirmed real adoption cost, not free: only `UiScope.row()`/`column()` accept the parameters directly, and reaching them from ordinary nested DSL usage (which resolves to the `ColumnScope`/`RowScope`/`AbsoluteScope`/`BoxScope` wrapper overloads) required threading `id`/`cacheKey` through those wrapper functions too -- a deliberate, additive expansion beyond the design doc's literal "wrappers don't need this" text, made necessary because direct inspection of `samples/ui-showcase` found *no* real call site that could reach `UiScope.row()`/`column()` without it (every shell/sidebar row/column is written inside a `BoxScope`/`ColumnScope` receiver). Piloted on `samples/ui-showcase`'s persistent shell (`UiShowcaseUi.kt`'s outer `row(id = "ui-showcase-shell-row", cacheKey = "static", ...)` and compact-mode `column(id = "ui-showcase-mobile-shell", cacheKey = "static", ...)`, plus `UiShowcaseChrome.kt`'s Preview/Code tabs row) -- each given a constant `cacheKey` because their direct children never call `.weight()` anywhere in the fixed source, so the cached answer can never go stale; the two content-viewport `column(id = "ui-showcase-*-content-viewport", ...)` calls were deliberately left unmigrated because they set `verticalScroll`, routing through `smartColumn`'s scrollable-container branch (`scrollPanel`) rather than `resolveMeasuredColumn` -- the only strategy this cache's `cacheKey` is wired into -- so `cacheKey` there would be accepted but silently do nothing. **Real measured number** (`UiShowcaseLayoutCostTest.measureShellRowCacheImpact`, steady-state, Checkout Form page): caching just the one outer shell row's `hasWeightedChild` trial cut per-frame trial-pass count from 15,381 to 7,690 (-50.0%) -- a large win from one call site because that row sits at the tree's root, so its own throwaway trial re-executes the *entire* shell subtree underneath it (sidebar + full page content) exactly once extra; removing that one redundant top-level trial removes a redundant execution of everything nested inside it. This does not change the Checkout Form page's own total trial count as reported by `measureRealShellFrameCost` (still ~7,690 -- that number was already *post*-cache, since `drawRealShowcaseShell`'s default `cacheShellRow = true` mirrors the shipped migration), confirming the win is real but, as the design doc predicted, gated on migrating individual call sites by hand -- the shell/sidebar's own internal `row()`/`column()` calls (inside `drawUiShowcaseSidebar`, `shadcnSidebar`, `shadcnSurface`) remain unmigrated (either no direct `row()`/`column()` call exists there, or -- for `shadcnSidebar`/`shadcnSurface` -- they resolve to `resolveVisualSurface`'s surface-styling branch, also outside `cacheKey`'s wiring, and out of `ui-core`'s ownership to touch here regardless). **Superseded by design, not yet by code (2026-08-21)**: `:awake:compose:*` is a retained, `Constraints`-based engine built as a peer of `:awake:ui` specifically to remove this row — see `docs/reference/compose-engine/`. It does not change anything documented above; `ui-core` is frozen but shipping, and this row stays `Diverges` until the Stage 4 proof gate passes. |
| A `WrapContent` parent's height being influenced by a `FillMax` child's size (Compose: a `wrapContentHeight()` parent constrains children to `Constraints(maxHeight = Infinity)` so a `fillMaxHeight()` child can't inflate it) | Explicitly guarded against via `contributesToWrapHeight`/`contributesToWrapWidth` flags passed to `context.recordMeasuredSlot()` in `RowScope.claimSlot()`/`ColumnScope.claimSlot()` | Faithful (now) | Verified current: `RowScope.claimSlot()` passes `contributesToWrapHeight = height != Dimension.FillMax` and `ColumnScope.claimSlot()` passes `contributesToWrapWidth = width != Dimension.FillMax`, both with inline comments citing this exact failure mode ("task #34"). Listed here for completeness, not as a deviation. |
| `LazyColumn`/`LazyRow` (virtualized/lazy child composition) | `lazyColumn(id, itemCount, itemHeight, modifier, key, itemContent)` / `lazyRow(...)` (`layouts/LazyList.kt`) | Diverges | Real virtualization now exists -- only items whose bounds intersect the viewport (plus a 2-item default overscan) run `itemContent` and emit primitives; a 10,000-item `lazyColumn` in a 300px-tall viewport composes 13 items (13 `Quad` primitives out of 15 total), confirmed by `LazyColumnVirtualizationTest`. Shape diverges from Compose's `LazyColumn { items(count, key) { index -> ... } }` in two deliberate ways: (1) every item must share one caller-supplied fixed `itemHeight`/`itemWidth` (`Dp`) rather than Compose's per-item lazy real measurement -- picked over a measure-and-cache-per-id model specifically to avoid re-triggering Awake's existing trial-measure double-execution cost (`docs/tasks/archive/2026-08-02-trial-measure-double-execution.md`) for every item scrolled into view; total content extent is pure arithmetic (`itemCount * itemHeight`), zero measurement of any item, on- or off-screen; (2) scroll state is an explicit `Modifier.verticalScroll(state)`/`horizontalScroll(state)` argument (reusing `ScrollContainers.kt`'s existing `UiScrollState`, not a new lazy-list-owned scroll model), where Compose's `LazyListState` is list-owned. `key` is threaded into `itemContent(index, key)` (unlike Compose, which keeps `key` internal to its slot-reuse machinery) so callers can build stable nested widget ids (`checkbox(id = "todo-$key", ...)`) -- Awake's immediate-mode `WidgetState` is keyed purely by the id string a widget receives and off-screen indices are simply skipped (never recycled into a different index's slot), so this is a convenience for callers building correct ids, not a state-corruption fix the way Compose's `key` is. |

## State hooks (`remember*`)

Source: `state/UiStateHooks.kt`, `state/WidgetState.kt`, `context/UiStateStore.kt`,
`context/UiRuntimeCoordinator.kt`, `state/UiScrollState.kt`.

Awake's `remember*` family (`rememberStateValue`, `rememberBooleanState`, `rememberFloatState`,
`rememberIntState`, `rememberPopupState`, `rememberScrollState`) is the immediate-mode
equivalent of Compose's `remember { mutableStateOf(...) }` family -- a per-widget value that
survives across frames. It did not previously appear anywhere in this doc; added 2026-08-21.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `remember { mutableStateOf(initial) }` / `remember(key1, ...) { ... }` -- identity is the call site's position in the composition's slot table, with `key1..keyN` as an *optional* extra invalidation trigger layered on top of that automatic identity | `UiContext.rememberStateValue(id, key = "value", initial)` / `rememberBooleanState`/`rememberFloatState`/`rememberIntState` (thin typed wrappers over it), returning a `UiStateValue<T>` backed by `WidgetState` (`UiStateHooks.kt`) | Diverges | Identity is 100% explicit and string-based, with **no positional fallback of any kind**. Verified end-to-end: `UiContext.rememberStateValue` calls `widgetStateInternal(id)` -> `UiRuntimeCoordinator.widgetState(id)` -> `UiStateStore.widgetState(id)`, which is a flat `widgetStates.getOrPut(id) { WidgetState() }` (`UiStateStore.kt:10`) -- a plain `HashMap<String, WidgetState>` keyed purely by the caller-supplied `id`; `WidgetState` itself is a flat `values.getOrPut(key) { default }` (`WidgetState.kt:17`) keyed by the caller-supplied `key`. `UiStateHooksTest.rememberStateValuePersistsAcrossFramesForTheSameId` proves this directly: it calls `ui.rememberIntState("counter")` from two textually different call sites (not inside any widget, not inside any composition-like tree) across two frames and the value persists -- there is no call-site/tree-position component to identity at all, unlike Compose where two different call sites can never collide by default. This is the same footgun *class* already documented for `animateFloat`'s `id` (MIRROR_MAP's Animation section below): an `id` built from a value that itself changes when it shouldn't restarts/loses state with no compile-time signal. State hooks add a second, distinct failure direction `animateFloat` alone doesn't foreground as clearly: **collision**. Two unrelated widgets that end up passing the identical `id` string silently *share* one `WidgetState` bucket -- no exception, no warning. `UiContext`'s one collision safety net (`UiContextFrameState.recordSemantic` throwing on a duplicate id, documented in `skills/awake-ui-authoring/SKILL.md`) does **not** cover this: that throw lives solely inside `recordSemantic` (`UiContextFrameState.kt:65`), a path a bare `rememberStateValue`/`rememberBooleanState`/etc. call never goes through on its own -- it only fires when a *widget* separately claims that same id as a semantic node. A caller reading/writing a state hook directly (not through a widget's own already-deduped id) gets silent, uncaught sharing on collision. See `docs/reference/ui-ownership.md`'s "Identity Params: `id` vs `testTag` vs `cacheKey`" table and its "State hooks have two identity levels" paragraph, and `skills/awake-ui-authoring/SKILL.md`'s "Every stateful widget needs a real, unique `id`" section, for the existing collision-avoidance guidance -- this row is the first to frame *why* Compose developers don't already have the instinct to worry about it (Compose's automatic call-site identity structurally prevents this exact bug; Awake's does not). |
| The delegated-property sugar: `var x by remember { mutableStateOf(0) }` | `var x by rememberIntState(id)` / `var flag by rememberBooleanState(id)` / etc. -- `UiStateValue` implements `getValue`/`setValue` (`UiStateHooks.kt:54-58`) | Faithful (ergonomics only) | The `by` call-site sugar reads identically to Compose (confirmed by `UiStateHooksTest.rememberBooleanStateCanBeUsedAsAPropertyDelegate`), which is exactly what makes the identity divergence above easy to miss -- the syntax similarity invites assuming full `remember` parity when the underlying identity model (row above) is completely different. |
| `remember`'s value is disposed when the composable leaves composition (Compose tracks composition membership and forgets state for a subtree that stops being composed) | No disposal. `UiStateStore`'s `widgetStates` map (and each `WidgetState`'s own `values` map) has no prune/cleanup path -- confirmed by inspection, neither type exposes anything beyond `get`/`set`/`remove` for one key at a time | Diverges | An `id` that stops being called simply leaves its `WidgetState` entry allocated in the `HashMap` for the rest of the owning `UiContext`'s lifetime -- there is no Awake analog to Compose's automatic forget-on-leaving-composition. Practical consequence: dynamically-keyed ids (e.g. per-row state in a list whose item set changes over time) accumulate unboundedly unless a caller explicitly calls `.reset()` (which only removes one `key` within one bucket, not the bucket itself) when an id stops being relevant. Consistent with the `lazyColumn`/`lazyRow` row below (Scope/DSL section above), which separately documents that off-screen indices are "simply skipped (never recycled into a different index's slot)" -- same no-disposal model, different surface. |
| Trial-measurement passes must not observe/mutate side-effecting state a second time (no Compose analog needed -- Compose has no "trial measure" concept, see the Scope/DSL section's `Diverges` row on the two-pass trial-measure model) | Writes are automatically suppressed during a trial pass; reads see the real, live, persisted value | Faithful (by construction) | Unlike `animateFloat*` (which each needed their own explicit, hand-added `isMeasuringInternal()` guard -- see the Animation section below), state hooks get trial-measure safety for free from the shared primitive: `UiContext.rememberStateValue` wires `UiStateValue`'s `isMeasuring` lambda straight to `isMeasuringInternal()` (`UiStateHooks.kt:87`), and `UiStateValue.value`'s setter plus `.reset()` both check it before writing (`UiStateHooks.kt:41-42`, `:50-51`) -- so a hook write during a trial pass is silently dropped rather than corrupting the value the real pass reads moments later. Reads are correct too, not just safe: the trial `UiContext` shares the exact same `stateStore` object as the real (source) context rather than starting from a blank one (`UiContextMeasureState.kt`'s `createMeasureContext`, `stateStore = sourceContext.stateStoreInternal()`, with an explicit comment: "a WrapContent/scroll trial pass re-executes the same content, and any persisted (`rememberStateValue`) branch inside that content... must see the real current value, not reset to its default"), proven by `WrapContentMeasurementStateTest`'s two regression cases (a single-level and a double-nested `WrapContent surface`/`column` sizing correctly against post-navigation persisted state). **The takeaway for new code**: prefer these hooks (or `animateFloat*`, which has the same guard) over hand-rolling a mutable value captured in a Kotlin closure inside `row {}`/`column {}` content -- a hand-rolled `var` has no trial-measure guard at all and will double-step. |
| `rememberScrollState(initial: Int = 0)` (paired with `Modifier.verticalScroll`/`.horizontalScroll`) | `UiContext.rememberScrollState(id, initialOffsetX, initialOffsetY)`, returning a `PersistedUiScrollState` (`UiScrollState.kt`) | Diverges (ergonomics) | Same name and purpose (a persisted scroll-offset holder consumed by a scroll modifier), same explicit-`id`-vs-call-site-identity divergence as the row above. Shape difference, not a bug: Awake's version is dual-axis in one object (`initialOffsetX`/`initialOffsetY`, matching `UiScrollState`'s own dual-axis fields), where Compose splits single-axis `rememberScrollState()` (paired with either `verticalScroll` or `horizontalScroll`) from a separate `rememberLazyListState()` for virtualized lists. |
| No direct equivalent -- most Compose codebases hand-roll `var expanded by remember { mutableStateOf(false) }` for a popup/menu-open flag | `UiContext.rememberPopupState(id, key = "expanded", initial)`, returning a small typed `UiPopupState` wrapper (`open()`/`close()`/`toggle()`) over `rememberBooleanState` | Not implemented in Compose | Awake-original convenience, not a mimicked primitive -- named and documented as such per `skills/awake-ui-authoring/SKILL.md`'s "New `Modifier`/layout extensions" rule (the same rule this doc's own header points contributors to before adding new Compose-mimicking surface). Every popup/dropdown/menu-open flag in this codebase gets the same three-verb API instead of five different hand-rolled booleans. |

`key`'s role deserves its own callout since it looks like Compose's `rememberSaveable(key = ...)` optional parameter but plays a structurally different part: Compose's `key` is a secondary disambiguator layered *on top of* automatic call-site identity (mainly needed when several `rememberSaveable` calls share one composable, e.g. inside a loop). Awake's `id` *is* the entire identity with no fallback; `key` (default `"value"`) is a second, independent axis -- which *field* within that one `id`'s bucket -- letting one stateful widget instance own several independent values (`rememberBooleanState(id, key = "expanded")` next to `rememberStateValue(id, key = "filter")` on the same widget). Changing `id` resets everything that widget owns; changing one call's `key` resets only that field. See `docs/reference/ui-ownership.md`'s "State hooks have two identity levels" paragraph, already documenting this convention.

## Animation primitives

Source: `UiAnimation.kt`, `UiEasing.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `animateFloatAsState(target, animationSpec = spring(...))` | `UiContext.animateFloat(id, target, initial, responsiveness, snapDistance)` | Diverges (ergonomics) | Conceptually the same "chase a target every frame" idea (an exponential-decay spring, `1f - exp(-responsiveness * dt)`), but the call shape is Compose's opposite: `animateFloatAsState` is state-driven (returns a `State<Float>` tied to composition identity, no explicit `id`), while Awake's version is immediate-mode and requires a caller-supplied stable `id` string used as the state-store key (`widgetStateInternal("__animation__$id")`). Forgetting to keep `id` stable across frames (e.g. deriving it from a changing value) silently restarts the animation with no compile-time signal, unlike Compose's automatic call-site/key-based identity. |
| `Animatable<Float>` + `animateTo(target, tween(durationMillis, easing))` | `UiContext.animateFloatTween(id, target, initial, durationMs, easing)` | Diverges (ergonomics) | Same immediate-mode-vs-state-object gap as above; retargeting mid-tween is deliberately matched to Compose's `animateFloatAsState` behavior (restart duration from the current animated value, not jump to `initial` -- confirmed in the function's own doc comment and `retargeted`/`effectiveStart` logic), so retarget semantics are faithful even though the calling convention isn't. |
| `rememberInfiniteTransition()` + `animateFloat(initialValue, targetValue, infiniteRepeatable(tween(...), repeatMode))` | `UiContext.animateFloatRepeatable(id, initialValue, targetValue, durationMs, easing, repeatMode, iterations)` | Faithful (ergonomics), Diverges (mechanism) | Parameter set matches Compose's `infiniteRepeatable`/`repeatable` split (`RepeatMode.Restart`/`Reverse`, `iterations` defaulting to "forever" via `Int.MAX_VALUE`, matching Compose's own `AnimationConstants.Infinite` sentinel pattern per the function's doc comment) -- genuinely faithful ergonomics. Mechanism diverges: progress is computed in **closed form** from an elapsed-time accumulator (`cycleIndex`/`cycleElapsedMs` derived from `elapsedMs / durationMs`) rather than Compose's frame-callback-driven `Animatable`; this is called out in-code as a deliberate choice to avoid a "one-frame-late flip" stutter bug the naive port had, not an oversight. |
| `AnimationSpec`/`tween`/`spring` as a reusable, composable value object (constructed once, passed around) | Two free functions (`animateFloatTween`, `animateFloat`) each taking their spec inline as parameters (`durationMs`, `easing`, `responsiveness`) | Diverges | Compose lets you build an `AnimationSpec` once and reuse/compose it (`repeatable(spring(...))`, pass the same spec to multiple `animateXAsState` calls). Awake has no equivalent value type -- each call site repeats its own `durationMs`/`easing`/`responsiveness` literals; `animateFloatRepeatable` is its own separate function rather than a `repeatable()` wrapper *around* `animateFloatTween`'s spec, even though the doc comment explicitly likens it to that Compose wrapping pattern. |
| `Easing` fun-interface + `LinearEasing`/`FastOutSlowInEasing`/`CubicBezierEasing` | `Easing` fun-interface + `LinearEasing`/`EaseIn`/`EaseOut`/`EaseInOut`/`CubicBezierEasing` (`UiEasing.kt`) | Faithful | Same fun-interface shape (`fun transform(fraction: Float): Float`, mirrored explicitly in the KDoc), same cubic-bezier Newton-Raphson-with-bisection-fallback solving approach Compose/WebKit use, same CSS-named preset curves (though named/pinned to CSS `ease-in`/`ease-out`/`ease-in-out` control points rather than Compose's own named `FastOutSlowInEasing` etc. -- equivalent shape, different preset library). |
| `updateTransition` / `MutableTransitionState` (multi-property, state-machine-driven transitions) | `UiContext.rememberTransition(id, targetState, durationMs, easing)` (`UiTransition.kt`) | Diverges (ergonomics, scope) | Real, not a stub: a stable `id`-keyed 0f-1f progress value that anchors the first-seen `targetState` as 0f and tweens to 1f (and back) whenever `targetState` compares unequal to that anchor, sharing one `animateFloatTween` lifecycle a caller derives N properties from via plain lerp math. Deliberately scoped down from Compose's real API: no per-property child registration (`transition.animateFloat { state -> ... }`) that lets multiple independently-configured properties register against one coordinator object -- that needs real multi-child bookkeeping the existing id-per-value `WidgetState` store doesn't cleanly support without a larger `UiAnimation.kt` refactor, so it was deferred rather than half-built. Calling it more than once per frame with the same `id` double-steps the underlying tween (same caveat `animateFloatTween` already has); the intended usage is one call per frame, then deriving multiple properties from the single returned float. No-ops during a trial-measurement pass "for free" by delegating all stepping to `animateFloatTween`'s existing `isMeasuringInternal()` guard -- it introduces no side-effecting state of its own. |
| Trial-measurement passes must not double-step a side-effecting animation (no Compose analog needed -- Compose has no "trial measure" concept) | Every `animateFloat*` function explicitly checks `isMeasuringInternal()` and returns the already-stored value without advancing state during a trial pass | Diverges (necessarily) | This guard exists purely because of the Row/Column trial-measurement divergence documented above -- it's a deviation forced by Awake's own two-pass layout model, not something a Compose port would ever need. The code comments explicitly reference an already-fixed real bug class for this exact issue (shimmer, commit `85f14821`), so treat any *new* side-effecting `UiContext` state read/write as needing the same guard, not just the three functions already covering it. |

## `graphicsLayer`

Source: `modifier/GraphicsLayer.kt`.

| Compose primitive | Awake equivalent | Status | Deviation detail |
|---|---|---|---|
| `Modifier.graphicsLayer { rotationZ = 45f; scaleX = 1.2f; scaleY = 1.2f; alpha = 0.5f; shadowElevation = 4f; clip = true; ... }` | `UiModifier.graphicsLayer(effect: UiGraphicsEffect)` + `UiGraphicsLayer(effects: List<UiGraphicsEffect>)` | Diverges | `UiGraphicsEffect` is still an empty marker `interface`, and `UiGraphicsLayer` is still just a `List<UiGraphicsEffect>` with `then()`/`has<T>()`/`without<T>()` set-composition helpers -- concrete effects (alpha, shimmer) are still layered on top rather than fields on the layer itself. What's changed since the previous read: one of those effects, `UiAlphaEffect(alpha: Float)`, now carries a real value instead of being a zero-property marker like `UiShimmerEffect` -- see the alpha-compositing row below. |
| Real per-pixel alpha compositing in the render pipeline | `UiAlphaEffect(alpha)` (`GraphicsLayer.kt`) applied by `UiContext.pushGraphicsLayerAlphaInternal`/`popGraphicsLayerAlphaInternal` (`UiAnimatedVisibility.kt`'s `withGraphicsLayerAlpha`), multiplied into every emitted primitive's color at `UiContext.emitInternal`/`emitOverlayInternal` via `UiDrawPrimitive.scaledByAlpha` | Faithful (alpha only) | Real, not a marker -- `withGraphicsLayerAlpha(alpha) { block() }` pushes onto a stacked alpha value (nested layers multiply, matching real compositing) that every primitive emitted anywhere inside `block()`, at any composite-widget nesting depth, has multiplied into its `Color.a` at the one central emission choke point -- no per-widget/per-renderer changes were needed, since every `UiDrawPrimitive` already carried its own `Color`. This is a CPU-side per-primitive alpha pre-multiply, not a real offscreen-buffer-then-blend compositing pass, so it's correct for fading a subtree in/out (the actual use case -- see `animatedVisibility` below and `UiPopup.kt`'s fade) but not for correctly blending overlapping semi-transparent content *within* one faded subtree. `animatedVisibility(id, visible, durationMs, easing, content)` (`UiAnimatedVisibility.kt`) is the real `AnimatedVisibility`-equivalent built on top of this: it drives the alpha via the existing `animateFloatTween` mechanism and keeps calling `content()` through the exit fade (instead of unmounting the frame `visible` flips false) until the tween settles at zero. |
| Real per-pixel scale compositing in the render pipeline | `UiScaleEffect(scaleX, scaleY, pivotX, pivotY)` (`GraphicsLayer.kt`) applied by `UiContext.pushGraphicsLayerScaleInternal`/`popGraphicsLayerScaleInternal` (`UiAnimatedVisibility.kt`'s `withGraphicsLayerScale`), carried on `UiDrawPrimitive.transform` (`UiPrimitiveTransform`) through to a real GPU vertex-shader transform in BOTH backends (`ui_quad.vert`/`ui_glyph.vert`/`ui_texture.vert`/`ui_rounded_quad.vert` for Vulkan, the `.wgsl` siblings for WebGPU) | Faithful (scale only, see `docs/tasks/2026-08-02-graphicslayer-rotation-scale.md`) | Real, GPU-side, not CPU-side geometry mutation -- unlike alpha (a CPU color multiply), scale changes geometry, so `UiDrawPrimitive.Quad`/`RoundedQuad`/`Glyph`/`Texture` each grew an optional `transform: UiPrimitiveTransform?` field threaded from `UiContext`'s emission choke point (`withTransform`, mirroring `scaledByAlpha`'s pattern) through to a new per-vertex `vec4` attribute (`scale.xy` + `pivot.xy`) in every UI vertex shader in both backends -- applied as `pivot + (position - pivot) * scale` before the screen-to-NDC transform. Batching investigation (see the task doc): same-type primitives already batch into one draw call via per-vertex-varying attributes (color already works this way), so scale/pivot rides along as one more per-vertex attribute -- no un-batching or instance-data redesign needed, scaled and unscaled primitives of the same type still coalesce into the same draw call.
