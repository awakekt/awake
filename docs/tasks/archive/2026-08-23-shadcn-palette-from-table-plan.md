# 2026-08-23: stop deriving shadcn's tokens, look them up

Status: **done 2026-08-23.** All five ordered steps landed, plus the three formalisation gaps.
`ShadcnReferenceTokens.kt` ships from `commonMain`, `createPalette` looks up the 26 and computes
11 (100 lines → 65), and the 13 `knownDrifted` entries and their machinery are gone — the only
surviving mention is one comment recording why they existed.

The reference pipeline (`docs/reference/shadcn-reference-pipeline.md`) already machine-extracts
**31 tokens × 7 base colors × 2 modes** from a pinned `shadcn-ui/ui` commit. `createPalette` then
*derives* those same tokens from one hue/chroma pair, and the tests lock in **13** places where the
derivation disagrees with the extraction.

We have the answers and compute an approximation of them anyway. This plan stops that.

## The split, measured

`ShadcnPalette` has 37 roles. Against the extracted table:

| | Count | Roles |
|---|---|---|
| **Available in the table** | **26** | `background` `foreground` `primary` `primaryForeground` `secondary` `secondaryForeground` `muted` `mutedForeground` `accent` `accentForeground` `destructive` `border` `input` `ring` `card` `cardForeground` `popover` `popoverForeground` + all 8 `sidebar*` |
| **Not in the table, legitimately derived** | **11** | `shadow`, `overlay` — fixed black at alpha, elevation over the page, not a theme colour · `destructiveForeground` — shadcn has no `--destructive-foreground`; its buttons hardcode white · 8× hover/pressed — shadcn expresses these as `hover:bg-primary/90`, alpha at the use site, not as tokens |
| Table tokens we do not model | 5 | `chart-1`..`chart-5` |

So the generator shrinks from 37 roles to 11, and every survivor is genuinely absent from shadcn's
CSS rather than merely uncomputed.

## Why the derivation cannot be fixed in place

`ShadcnReferenceTokenExpandedTest` already found and documented the root cause: `createPalette`
derives every token for a base colour from **one** `hueDegrees`/`chroma` pair scaled by fixed
multipliers, while shadcn hand-tunes hue *and* chroma per token within the same base colour — real
`stone`'s `foreground` is `oklch(0.147 0.004 49.25)` while its `primary` is
`oklch(0.216 0.006 56.043)`, different on both axes.

A single-pair model structurally cannot reproduce that. The only way to make it match is to become a
per-token lookup table, which is what the extractor already produces.

`Neutral` is the exception with zero drift, and it is exactly the base colour where hue and chroma
are both zero — so the single-pair model is trivially right there and wrong everywhere else. That is
why six of seven drift and why nobody noticed for a long time: the only colour anyone checked was
the one the model happens to get right.

## Options

| | Pros | Cons | Verdict |
|---|---|---|---|
| **A. Keep deriving** | No change. Generates a palette for any hue, including base colours shadcn does not define | Six of seven shipped base colours are visibly wrong. 13 drift entries stay locked in as furniture. The generative capability is unused — we ship exactly the 7 shadcn defines | **No** |
| **B. Table for 26, formulas for 11** | Drift becomes zero by construction for every shadcn token. 13 `knownDrifted` entries delete. `createPalette` drops ~70%. Accent overlay is untouched. The 11 survivors are honestly "ours", not failed approximations | The table is data in the repo — a bumped pin means regenerating it (already scripted). A custom base colour outside the 7 needs a fallback | **Yes** |
| **C. Table for everything, hand-write the 11** | No computation at all | Hand-writing 11 × 7 × 2 = 154 values that are currently one formula each. Re-introduces exactly the hand-typing the pipeline exists to remove | **No** |

**Take B.** The hover/pressed formulas are the one place a formula genuinely beats a table: they are
Awake's own interaction states, they are not shadcn tokens, and shadcn's own answer — alpha at the
use site — is a formula too.

## Where the table lives

The extracted table is currently in `commonTest` (`ShadcnReferenceTokens.kt`), because until now it
was only a test fixture. Under B it becomes the palette's source and has to move to `commonMain`.

That is the one real design consequence, and it is worth stating plainly: **the reference stops
being something we check against and becomes something we ship.** The check does not disappear —
it inverts. Instead of "does our derivation match shadcn", the test becomes "does the shipped table
still match the pinned upstream", which is a regeneration check and strictly cheaper.

## Formalising the pipeline

Three gaps, independent of the palette decision.

### 1. Nothing detects a hand-edit of the generated file

`ShadcnReferenceTokens.kt` is generated by `tools/extract_shadcn_tokens.py` and committed. Nothing
checks that the committed file still equals what the extractor produces. Someone "fixing" a value by
hand would silently break the chain back to upstream, and every test would stay green — the exact
failure the pipeline was built to remove, reintroduced one level up.

**Fix:** a check that re-runs the extractor and diffs against the committed file. It needs the
pinned checkout, so it belongs wherever that is available rather than in the default CI path.

### 2. The pin is verified by hand, when someone remembers

`shadcn-reference-pipeline.md` says to re-run the fetch against the current upstream commit before
trusting it for a release. That happened today, manually: the registry at `PINNED_SHA` is
**byte-identical** to `main` — 1,086 lines, no drift. Nothing schedules the next check.

**Fix:** a scheduled job that fetches `apps/v4/registry/themes.ts` at `main`, diffs it against the
pin, and reports. It must **report, not bump** — moving the pin changes what the theme has to match,
which is a visual decision.

**Trap worth recording:** `apps/v4/app/globals.css` is the docs site's own theme and *has* diverged
from the registry — its light `--foreground` is `oklch(0% 0 0)` where the registry says
`oklch(0.145 0 0)`. Checking the wrong file produces a false drift alarm. The registry
(`apps/v4/registry/themes.ts`) is the source that ships.

### 3. The pixel layer is not a gate and does not say so

`capture_shadcn_local.py`, `tools/shadcn-reference-app` and the four `shadcn_parity_*.json` files
have no CI reference, no Gradle task and no Kotlin test driving them. They were touched two days ago,
so they are in use — but manually.

**Fix:** decide and label. Either wire a task so it can fail, or state in the pipeline doc that it is
a human-in-the-loop investigation tool. Tooling that looks like a gate and is not is worse than
tooling that says it is manual.

## Order

1. Move `ShadcnReferenceTokens.kt` to `commonMain`. Mechanical; it imports only `Color`.
2. `createPalette` looks up the 26, keeps the 11 formulas. Accent overlay untouched.
3. Delete the 13 `knownDrifted` entries and the machinery that reads them.
4. Invert `ShadcnReferenceTokenExpandedTest` into a regeneration check.
5. Retire `ShadcnReferenceTokenTest`'s five shadcn-compose-sourced tests — superseded, and their
   citations point at a third party's doc comments rather than upstream.
6. The three formalisation gaps above, in any order.

Steps 1–3 are one change and should land together; the tests in between would be asserting a
half-converted palette.

## Not in scope

- Bumping the pin. Verified current today; moving it is a visual decision with its own review.
- `ShadcnAccent`'s 17 overrides. Hand-picked Tailwind values with their own provenance, outside
  `themes.ts` and outside this plan.
- The `chart-1`..`chart-5` tokens. Extracted already, modelled by nothing.
